# Agent 首页提示与示例：修复及数据诊断

日期：2026-09-10。范围：前端体验修复、原服务只读诊断与示例验证；不修改 API、RAG、价格采集或数据库。

## 1. 本轮改动

- 临时通知从聊天区域移至独立 `position: fixed` 层，不参与页面高度计算，默认 6 秒关闭。
- 支持手动关闭、鼠标悬停和键盘聚焦时暂停计时；新提示替换旧提示并重置生命周期，组件卸载后清理计时器。
- 保留礼貌播报的 live region、文本转义、移动端宽度约束和减少动态效果设置。
- 身份核验失败、过期等需要用户操作的状态独立展示，不能随通知消失；核验成功前仍隐藏历史并阻止业务请求。
- 首页示例单独维护为经过数据验证的目录，再按能力状态过滤；不再由“能力可用”推导任意示例一定可回答。
- 示例仍走原 `explicit_intent → submitRequest → SSE` 通路，不写死答案或价格，不绕过工作流、证据校验或幂等控制。

## 2. 原示例为什么无法回答

以下是既有正式入口、匿名访客身份、显式意图、SSE 的合成输入实测，不是仅检查服务健康。

| 示例 | 实际结果 | 原因与边界 |
| --- | --- | --- |
| 快件丢失理赔通常需要哪些材料？ | HTTP 200，SSE `done`，`completed / no_match`，`reason_code=llm_rejected`，约 7.96 秒 | 有相关条文，但回答所需的材料清单证据不足；不是网络超时或意图路由失败 |
| 查询 iPhone 16 Pro 256GB 的参考价格 | HTTP 200，SSE `done`，`completed / no_match`，约 0.20 秒 | 解析为 APPLE / iphone 16 pro / 256GB；当前有价产品覆盖未包含该型号，不能用其他型号冒充 |

原政策问题的检索返回 5 个候选，重排分数约 0.87～0.98，但内容是赔偿责任、保价规则、
投诉渠道等，并没有直接列出办理理赔所需材料。这说明 **相关性高不等于能够回答问题**；
答案充分性校验拒答有合理依据。本次不通过调低阈值或撤销引用约束来强行产出材料清单。
该结果只说明当前检索结果不足，不能推断整个知识库绝对不存在相关内容。

价格库在本次检查时已经有 `product=103`、`sku=1114`、`price_current=1114`，覆盖 5 个品牌。
这与 6A-4 发布时的空库快照不同；不应继续把“空库”作为当前故障结论。本轮没有执行导入或采集。

## 3. 替代示例与验收口径

| 新示例 | 正式通路结果 |
| --- | --- |
| 快件丢失后，消费者可以通过哪些渠道投诉？ | `completed / success`，4 条政策证据，约 9.39 秒 |
| 查询 iPhone 17 256GB 的参考价格 | `completed / success`，5 条价格候选，约 0.30 秒 |

另验证“向邮政管理部门申诉前，需要先向快递企业投诉吗？”返回成功及 4 条证据，作为候补问题。
上述耗时是单次观察，不是 SLA、延迟分位数或代表性质量评测；示例在数据源变动后仍需重验。
政策示例不新增 Query Understanding 模型调用，但会使用原 RAG 的判定及生成能力；价格示例为只读查询。

自动回归包括：计时 / 重复通知 / 阅读暂停 / 卸载清理、可访问性与转义、可用性过滤、
身份失败操作保留，以及实际客户端组件把两个示例绑定至正确 `explicit_intent`。
计时与父组件生命周期在无浏览器、无网络的测试中验证；SFC 客户端测试和 SSR 合同测试分别运行，
不加载 `.env`，不把真实响应或密钥写入测试夹具。

本地结果：89 项 Web 测试（新增 19 项）、1089 项 Python 测试通过；类型与两种隔离构建通过。
浏览器在本机合成身份服务上验证：通知出现前后聊天区的 top / height / scrollHeight 均未改变，
通知位于聊天区外的 fixed 层，计时到期后关闭按钮消失。该浏览器夹具不连接真实政策或价格服务；
真实示例结果来自上述正式入口的 API / SSE 验证，两类证据分别记录。

## 4. 后续修复顺序

1. **补充可回答性评测**：把“理赔材料”保留为证据不足的负例，把两个新示例作为人工烟测用例。
   分开记录路由、检索、答案充分性、工具结果和 UI 展示，避免把所有 `no_match` 归因于模型。
2. **补材料清单知识**：在获得可信、可使用的企业办理指南后，按企业、业务类型、保价状态、
   地区和有效期结构化入库；通过澄清收集场景，检验检索召回及引用是否真正覆盖材料要求。
   尚未拿到指南时继续诚实拒答，不能把普遍建议伪装成该企业正式要求。
3. **治理政策适用性**：此次候选含较早资料，`validity_status` 为 unknown；增加有效期、草案 / 正式、
   地区和来源优先级审查。示例能回答并不等于资料现行、全国适用或法律意见。
4. **补历史型号价格覆盖**：确认是否需要支持已不在当前商城报价目录中的型号；如需要，接入经授权的
   历史观察或补充来源，并展示日期与在售状态，不能将旧价当实时价格。覆盖不足时可提示可查询型号，
   但不能静默替换用户指定的型号或容量。本次解析正常，无需为这个负例放松型号匹配约束。
5. **维护示例目录**：采集 / 入库更新或上线前重新运行少量示例检查，审核后更新目录。
   未来可增加独立的业务覆盖检查；服务 readiness 仍只负责依赖状态，不能混同数据覆盖与答案质量。

## 5. 发布约束

用户批准本轮提交、推送并更新原网页。仅构建和替换 Web，沿用现有 HTTP 入口、代理配置及
Debian Nginx 基础镜像；API、RAG、价格库、访客签名与 Agent 状态库保持不变。
发布前验证远程 CI 和旁路页面，切换失败恢复当前 Web；保留上一前端镜像及容器。
具体上线版本、镜像摘要、CI 链接、检查结果和回退入口保存在服务器私有发布记录中。

## 6. 复盘要点

这次问题体现了三个不同层面的契约：通知的交互生命周期、工具的服务可用性、业务数据的可回答性。
定位时先按 SSE 终止状态和 reason code 区分调用失败与正确拒答，再核对实际数据覆盖；
修复体验问题的同时保留身份隔离、引用和型号匹配边界，而不是为了让示例“有答案”而放松约束。
