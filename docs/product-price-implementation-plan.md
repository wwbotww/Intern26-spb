## 1. 目标、范围与前置事实

### 1.1 最终目标

在不访问价格 V1 业务表的条件下，让同一套价格查询核心同时支持电子设备和已有生鲜来源，
并覆盖当前设备 Tool 的有效能力。新 Agent 使用 `product_price` 意图；保留的
`/v1/chat` 设备入口通过薄协议适配调用新核心，不再拥有旧 SQL 或另一套匹配算法。

“全品类”表示数据模型与扩展边界通用，不表示首轮已经拥有任意商品的数据和查询规则。
API V1/V2、价格数据 V1/V2 和 State 版本不是同一版本线，见[数据源边界](data-sources.md)。

| 首轮必须覆盖 | 首轮不包含 |
| --- | --- |
| 设备：品牌、产品型号/系列、已证明的规格、当前/原价、状态、来源、观察时间 | 扩大官网发现范围、补全所有历史型号或尚未解决的定制组合 |
| 生鲜：已有来源的品名/品种、地区/市场、批发或零售、原始报价与标准单位价 | 任意新来源、跨平台商品自动合并、无证据的单位换算 |
| 最新有效观察；无金额状态；可取得时单列最近有价历史 | 任意日期查询、价格趋势、跨日统计、预测或推荐最低价 |
| 类型化理解、补槽、候选选择、JSON/SSE、旧历史读取和安全切换 | 自由 ReAct、模型生成 SQL、新微服务、通用插件平台或多副本改造 |

采集侧负责原生写入 V2，不由 Agent 搬运 V1 数据。能力替换不承诺 V1 历史连续性；
旧表物理保留或删除属于生产者管理，删除必须另获授权。

### 1.2 改造前基线与必须补的缺口

| 边界 | 当前实现 | 本次改变 |
| --- | --- | --- |

| 设备检索 | 产品硬身份约束 → 产品排序 → 产品内规格过滤 | 保留匹配语义，替换数据来源和证据对象 |

## 2. 目标模块边界

~~~text
Agent product_price → ProductPriceTool ─────────┐
                                              ├→ ProductPriceQueryService
V1 device_price → 设备协议适配器 ────────────────┘       ├→ Device / Fresh 匹配策略
                                                      └→ V2PriceReadRepository（SELECT）
                                                             ↓
                                                   统一证据与类型化结果
                                                             ↓
                                                  API 白名单投影 → Web / Eval
~~~

- **Domain**：查询条件、候选、金额/状态证据、业务结果和只读 Port；不导入 MySQL、Web 或 LangGraph。
- **Repository**：固定查询、参数绑定、行映射与关联完整性；不理解自然语言，不按品牌复制 SQL。
- **Query Service / 策略**：设备身份与规格匹配、生鲜条件筛选、候选生成、可比性和来源约束。
  先用两个明确策略，不建设可动态执行的插件或通用查询语言。
- **ProductPriceTool**：类型化 Command 到 Service 的应用入口；不把爬虫写入模型直接暴露给 Agent。
- **LangGraph**：理解、补槽、选择、执行、校验、恢复、收据和预算；Node 不包含价格 SQL 或品牌规则。
- **API / Web / Eval**：分别维护公开投影、展示和独立验收；不将全项目 DTO 塞入 `packages/contracts`。
- **应用生命周期**：价格连接池与 Service 只初始化/关闭一次；V1 包装器和 Agent Tool 只借用。
  政策 Tool 现有复用不随本次价格迁移重写。

下列是实施落点，不表示全部已实现；实际交付范围见状态页。相对路径从 Assistant `src/spb_assistant_api/` 起算。

## 3. 消费契约与查询不变量

字段、关联、金额/单位、来源日及首轮消费限制统一维护于
[价格消费合同](../apps/assistant-api/docs/integrations/product-price.md)；
[合成 manifest](../apps/assistant-api/tests/fixtures/product_price/manifest.json)定位生产者未提交快照及夹具。
该合同的本地冻结不等于生产者发布承诺或真实库验收。

B/C 实施时必须保持：

- current 指针与 observation/revision/地区一致；设备使用当前有效可信 match，生鲜不强制标准商品关联。
- 原始报价与标准单位价分开；最新无金额状态不能被旧金额覆盖；历史暂限可证明同一 revision 的更早观察。
- 产品身份硬约束先于规格筛选；SQL 候选有界、先产品后规格、固定排序与参数绑定，不接受动态 SQL/JSON 路径。
- 多条 SQL 保持有界一致性，跨用户等待不持有事务；不能用 `SELECT 1` 或 FakeEngine 代替业务投影验收。
- 最新/当天需求保留真实时间；freshness 阈值待来源维护人确认；未知或超期不能伪装实时，也不是必然断连。
- 未支持的日期/趋势、单位或来源范围明确拒绝，不默默改查或跨口径汇总。

## 4. Query Understanding、Routing 与结果契约

### 4.1 拟定类型边界

以下是目标类型边界，字段与接口设计选择见消费合同；公开 schema 到 D 阶段实现时再同步生成。

| 类型 | 内容与责任 |
| --- | --- |
| `ProductPriceSlots` | 类目选择 `device/fresh/unknown`；有辨识字段的设备/生鲜条件联合类型；价格口径、地区/市场、单位需求及时间约束 |
| 设备条件 | 品牌、产品文本/型号、容量、内存及受支持规格；不让 LLM 生成 catalog/variant ID |
| 生鲜条件 | 品名/品种、地区/市场、批发或零售、期望单位；不把未知品牌当必填项 |
| `ProductPriceCommand` | 已通过规则和补槽校验的条件、查询模式、可选的服务器候选引用；原句只作上下文，不作为任意执行参数 |
| `ProductPriceCandidate` | 服务器提供的有限候选及可读标签；内部绑定 owner、query、约束指纹、身份和过期条件 |
| `ProductPriceEvidence / Data` | 商品身份分型、原始报价、标准单位价、状态、来源与时间；历史价在单独字段，不混入当前报价 |

不是把设备专有字段全部改成可选，再要求每个消费者猜字段组合。
价格结果公共部分统一，设备/生鲜身份与条件用有 discriminator 的联合类型约束。

### 4.2 路由与补槽规则

1. 新 Agent 只注册一个价格能力 `product_price`，由类目策略解释条件；旧意图仅保留必要的兼容解码。
2. 规则优先，模型只在既定 fallback 条件下补充结构化理解。模型 Schema、Prompt、规则输出和 Eval 镜像同步演进。
3. 重量必须结合“寄/运费/寄达”等寄递语境判断；商品的斤、公斤、500g 是计价/商品条件，不能单凭重量路由资费。
4. “苹果多少钱”先区分水果与设备；有“iPhone / 容量”等证据才明确设备，有商品/单位语境再判生鲜。
5. 设备缺产品身份先补型号；生鲜补会改变价格口径的品名、地域和批发/零售条件。
   用户明确要查看多个来源时可分别列出带口径的有限结果，不强迫虚构唯一市场。
6. 自然语言补槽复用已有冲突确认；更换类目、型号、地区或价格口径时清理失效的依赖槽位与候选。
   模型不能覆盖已确认条件或把“没有数据”解释成“应该改查别的商品”。

这些是必须新增的确定性回归输入，不是代表性模型质量指标：

| 合成输入 | 目标行为 |
| --- | --- |
| iPhone 16 Pro 256GB 价格 | `product_price/device`，保留型号与容量硬约束 |
| 苹果多少钱 | 澄清水果或设备，不直接执行错误 Tool |
| 苹果一斤多少钱 / 苹果 1kg 多少钱 | 生鲜价格；缺地区/口径时补槽，不路由资费 |
| 上海黄瓜零售价格 | 生鲜；地区与零售口径进入 Command |
| 北京鸡蛋批发价 | 生鲜；不拿其他地区零售价充当答案 |
| 从上海寄到北京 2 公斤多少钱 | `postage`，保留现有资费流程 |
| 不是问运费，我问这箱苹果价格 | 按纠错语义转商品价格，不被重量或历史意图锁死 |

现有 Hybrid 不会修正所有高置信规则误判，因此不能只接模型、不修改重量路由和补槽逻辑。
默认开发与 CI 不调用真实模型；任何新的付费联调都需重新授权。

## 5. Stateful Workflow、Agent Loop 与失败处理

### 5.1 结果驱动的有界澄清

沿用现有 Graph，新增价格结果分支：

~~~text
understand → decide → 缺条件：clarify / interrupt → resume → understand
                    条件足：execute_tool → validate_result
                                            ├─ 有可靠事实 / 正常无匹配 → compose → END
                                            ├─ 需要选择候选 → decide → clarify / interrupt
                                            │                         → 校验选择 → 再执行
                                            └─ 技术失败 → recover → 有界 retry 或终止
~~~

价格 `need_more_info` 不能继续被通用 compose 直接标为 completed；合法候选进入等待用户状态。
选择须经独立类型化输入，例如拟新增的 `price_selection.candidate_token`，
同时扩展公开 RequiredInput，而不是把 JSON 塞进 `message` 或接受任意槽位字典。
自然语言“第二个”也只能映射当前有效候选，不能凭模型创造数据库标识。

候选存入现有会话 State，不新建跨用户缓存服务。选择时核验 owner、query、约束指纹、有效期和当前身份；
旧 token、跨访客、跨查询、改题后的 token 均拒绝。最终报价重新读取同一身份的最新事实；
身份失效时要求重新查询，不替换相似商品。

### 5.2 预算、幂等与恢复不变量

| 项目 | 首轮设计 |
| --- | --- |
| 逻辑 Tool 调用 | 每个价格 query 最多 2 次：发现/直接报价 + 用户选择后报价；无歧义通常 1 次 |
| 技术重试 | 每个 query 最多 1 次，沿用 retryable 白名单；技术重试复用同一逻辑调用身份，不增加候选搜索轮次 |
| 澄清 | 每个价格 query 最多 3 轮，超限明确结束/请重新提问；其他业务预算不随之全局放大 |
| 执行边界 | 保留现有 step、recursion、请求 deadline 和数据库超时；等待用户不算数据库运行时间 |
| resume | 保留 query_id、已用 Tool/retry/澄清预算；只更新本轮 deadline 等允许字段，不能用刷新/补槽重置额度 |
| 重放 | 同一已完成 call/message 返回原结果、来源和时间；新查询生成新 query_id 并重新取数，不把收据当业务缓存 |

当前默认 `max_tool_calls=1`，而 clarify resume 保留 query 计数。因此预算和分支必须一起改，
不能只画出两次调用却沿用单次上限。Service 内必要的多条有界 SQL 不等于多个 Agent Tool 调用，
需分别测量；在一次不中断的受控执行中，2 个逻辑调用加 1 次 retry 最多产生 3 次 Tool 实际尝试。
不据此宣称硬崩溃窗口下的 exactly-once 或外部调用绝对上限。

实质改题须经现有确认流程结束旧 query，再创建新 query；普通补槽和断线恢复不是改题。
候选选择形成新的 Command / call 身份；完成的发现收据不能覆盖最终报价收据。

### 5.3 业务结果与故障分类

| 场景 | 行为 | 是否重试 |
| --- | --- | --- |
| 条件不够 / 多候选 | `need_more_info` → 收集输入；与上游故障分开 | 不自动重试 |
| 可信数据中无此型号/地区/规格 | `no_match`，不建议虚构替代价 | 否 |
| 有明确无金额状态 | 返回状态证据；报价缺失不等于商品不存在 | 否 |
| 仅有旧观察 / 日期不符合 | 保留真实时间，使用明确 reason/warning；不称作今天现价 | 否 |
| 未支持类目、计价或时间范围 | 明确范围限制，可让用户重新选择支持范围 | 否 |
| DB 超时/断连 | 对应既有 timeout/unavailable taxonomy，公开正常服务提示 | 仅受预算允许的暂时故障 |
| 缺表列、单位矛盾、关联串数据、非法状态 | contract violation / 不可用并告警，不返回不可信金额 | 否 |
| 候选过期、非法选择、旧状态无法恢复 | invalid input / state conflict 等稳定错误，请重新查询 | 否 |

能力未装配时仍在采集多余槽位前阻断。readiness 至少区分连通性与 V2 必需投影兼容性；
数据覆盖/新鲜度走独立只读诊断，不在每条聊天执行全表计数。
遥测复用已有 Trace / Node OTel，只增加有限的类目、结果与失败码；
不用商品名、用户原句、数据库 ID 作高基数标签，不公开原始证据路径或连接信息。

## 6. API、旧会话与部署兼容策略

1. **新业务核心只有一套**：`product_price` 对应新 Agent Command/Data；V1 设备入口只做输入与结果投影。
   V1 不能表达无金额状态时，返回真实的状态说明与空价格证据，不造价；
   多候选保持单轮协议的补信息提示，不偷偷启动会话。金额可表达的旧能力必须逐项回归。
2. **不承诺旧 Agent Web 能理解新结果**：采用 API/Web 协调升级，而非长期维护两套价格会话协议。
   D 阶段加入轻量、显式的客户端契约版本门禁，字段和值按消费合同冻结选择实现。
   会话推进与快照读取在发送新类型或打开 SSE 前检查，不支持的客户端收到既有错误信封下的
   `agent_client_upgrade_required` 并提示刷新。服务身份入口与 V1 保持原合同；代理、CORS、Eval 一并更新。
3. **旧完成历史可读**：保留 `device_price` 历史 DTO 的验证/渲染，不批量改写成 `product_price`，
   不补写缺失单位或新来源。新 Web 能展示旧结果；完成收据重放仍是原结果。
4. **旧未完成价格查询不猜迁移**：新增 State 版本及显式迁移测试；旧 device pending command、
   interrupt 或未完成 claim 无法证明安全时，按现有兼容失败语义要求用户从新会话发起价格查询，
   原会话保留可安全读取的历史。
   不自动恢复执行、不重算旧参数指纹、不删除原 checkpoint/收据。非价格工作流保持原恢复能力。
5. **新旧数据库版本分开**：正式 V2 价格装配不自动 fallback 到 V1。未切换环境可在部署级保持旧发布；
   切换后旧表无权限也必须工作。旧 DTO 解码仍被历史使用，不等于允许保留旧表查询代码。
6. **回滚不是降级状态库**：切换前停服并整库备份，升级/恢复只写新卷或新目录。
   回滚旧 API/Web 需回到经验证的旧状态快照并保留新卷；切换后的会话处理与潜在丢失窗口须先确认。
   更安全的局部止损是关闭价格能力、保留新 Runtime 和其他业务，不自动改查冻结的 V1 数据。

## 7. A～E 实施阶段与交付门禁

以下描述各阶段交付门禁，实施进度唯一维护于当前状态。阶段按门禁推进，不按承诺日期自动进入下一阶段。
默认每阶段提交可独立回归的改动；提交、推送、真实联调和发布按当次授权执行。

### A. 冻结消费者契约与旧能力基线

输入：当前 Assistant 代码；采集侧 V2 schema、阶段 I 规格/状态定义与脱敏样例。

- A1：把现有设备解析、身份/规格过滤、当前/原价、状态与来源行为整理为对照用例；记录明确不支持项。
- A2：和生产者核对消费字段、有效 match、官方来源、地区、质量门禁、日期和无金额状态；
  形成 Assistant 内的只读合同与 fixture manifest，注明哪些字段仍是 provisional。
- A3：冻结内部模型草图、公开价格字段、候选输入和客户端契约门禁；列出旧历史/客户端处理用例。
- A4：准备设备、生鲜、无金额、串关联、单位冲突等合成夹具；登记真实样例和只读权限缺口。

输出：合同、基线用例、夹具清单、更新后的 PRICE-G 缺口表；不改生产 SQL/数据。
合同入口为 `apps/assistant-api/docs/integrations/product-price.md`，
夹具放在 `apps/assistant-api/tests/fixtures/product_price/`，用 `manifest.json` 绑定来源与版本。
第三节只保留摘要和链接，不在两份文档重复维护字段细节。
退出条件：金额/单位和身份边界无自相矛盾；所有未确认项有负责人角色与阻塞阶段。
已冻结部分可进入 B；未确认部分仅跑明确标为 provisional 的合成测试，不能获得真实验收结论。

### B. V2 只读 Repository 与统一查询核心

输入：A 已冻结的最小合同和夹具。可在采集侧真实设备数据就绪前推进。

- B1：实现 Domain / Port / 固定 MySQL 查询；打通 current 指针到可信 observation 的公共证据路径。
- B2：实现设备规范层和生鲜来源层两种召回，不强制生鲜 inner join 标准商品；约束并测试查询上限和顺序。
- B3：实现金额/状态联合校验、单位分离、可选历史合同、来源时间与 freshness 标记。
  当前历史 SQL 允许保守不返回；未经证明的同一时点 correction 终点不能按 ID 大小猜测，后续按 PRICE-G11 补有界检索。
- B4：实现连接与必需 schema 投影探测、失败映射和单一资源生命周期；保留既有业务默认装配，不上线新能力。
- B5：新增专用 MySQL 5.7 / 8 集成测试任务。只建 V2 表，运行账号只有 V2 SELECT 权限；
  同时验证 V1 表完全不存在、以及存在但不可访问两种场景。SQLite 仅用于 Agent State，不替代 MySQL 验收。

输出：V2 只读核心、合成数据集、真正执行 SQL 的隔离集成测试；无自然语言 UI 要求。
退出条件：设备/生鲜/无金额事实都能通过同一核心读取；非法事实被拒绝；
不只用 FakeEngine 证明 SQL；默认 CI 不读取真实 DSN，不隐式加载 dotenv 或进行采集。

### C. 设备能力替换与 V1 薄协议适配

输入：B 核心；A 冻结的设备对照矩阵。采集侧单品牌夹具可先使用，真实覆盖仍留待 E。

- C1：将设备纯解析/硬匹配迁入可复用策略；品牌、产品、型号变体与规格约束不放宽。
  修复 A 基线暴露的 Pro→Pro Max 替代和基本款/Pro 混合问题，将 strict xfail 目标转为通过。
- C2：用统一 Service 实现设备报价，保持原价未知、SKU 标识可选、非在售和来源时间语义。
- C3：改造 V1 设备包装器和资源装配；在受控测试配置验证 V1 与新 Tool 共用一套 Service，初始化/关闭各一次。
- C4：针对同一批合成或获准证据比较旧语义基线与 V2 输出；核验字段、身份、金额和失败原因，不比较不同抓取日的数字相等。
- C5：清点旧 Repository、Record、Device Tool 的依赖；生产默认切换前保留旧发布回退点，
  E 收口时移除旧 SQL 路径，不把 V1 业务库做成隐形 fallback。

输出：具备设备旧能力的 V2 核心与 V1 HTTP 兼容适配；已知覆盖缺口说明。
退出条件：旧有效行为矩阵全通过，明确型号负例不误答；原价和状态不降级；两种 HTTP 复用不导致双重关闭。
此时不能宣称全品类 Agent 已完成，因为 D 的槽位、候选和公开结果尚未接入。

### D. 统一 Agent、Web 与离线验收

输入：B/C 核心与结果合同，默认使用隔离夹具；不等待物流真实接口或新模型授权。

- D1：加入 `product_price` 意图、联合槽位/Command、能力描述；同步规则、模型 schema/prompt 与组件 Eval。
- D2：修正重量/单位路由，完善类目/地区/口径补槽与覆盖确认；新增价格候选及依赖槽位失效规则。
- D3：实现 Graph 结果澄清分支、2 次逻辑调用/1 次 retry/3 轮澄清预算、选择验证、恢复和收据隔离。
- D4：新增统一价格 DTO、公开候选与契约门禁；同步根 OpenAPI、生成 TS、运行时校验、Eval 独立模型及快照读取。
- D5：新增通用价格卡片和设备/生鲜细节；支持无金额状态、原始/标准单位、来源/地区/时间、候选点击与旧卡片读取。
- D6：完成 State 迁移、旧 pending 安全拒绝、原结果重放、新查询刷新；测试 JSON/SSE、浏览器刷新、双访客和非法 token。
- D7：将新合成场景加入默认离线门禁、Web 双模式构建及部署演练；政策和三类物流的原有行为必须不退化。

输出：端到端离线可用的新 Agent 价格能力、契约生成物、回归证据和升级操作草案。
退出条件：第八节离线门禁全部通过；合成结果不能计入真实数据成功率，规则测试不当作模型泛化质量。

### E. 真实数据核对、切换与清理

输入：D 通过；采集侧目标范围真实 V2 链路验收、SELECT 授权、schema/样例合同和已确认的发布回退窗口。

- E1：先对已有生鲜及一个设备品牌进行只读核对，再按采集侧覆盖扩大到五品牌。
  检查身份/规格/match、金额/单位、状态/原价、来源时间和缺失样例，不以记录总数替代语义验收。
- E2：受控环境验证只给 V2 SELECT 权限仍可执行 Agent 与 V1 设备入口；不读取 V1 生产表来在线双查。
  对照以相同证据的基线为准，允许新采集价格随时间变化。
- E3：记录来源覆盖与 freshness 策略、查询耗时和有界 SQL 行为；若需索引或数据修复，提交生产者处理，不由 Agent 自动建索引或改行。
- E4：验证远程 CI 后，按[部署操作](../deploy/agent/README.md)停服备份并协调发布 API/Web；
  保留身份/Origin 和单实例约束，其他依赖不重建。价格未装配时正常不可用，不注入 Fake。
- E5：目标入口核验价格 JSON/SSE、补槽/候选、旧历史、新查询及双访客；回归政策、物流不可用提示和 V1 模式。
- E6：完成价格能力关闭/恢复与回滚演练，移除应用生产路径中的 V1 价格 SQL 和双业务实现；
  保留仍有历史引用的解码器。关闭有证据的缺口，更新状态、服务运维与复盘。

退出条件：只依赖 V2 的目标设备能力矩阵和已有生鲜范围通过真实验收；
当前指针、无金额状态、来源和单位均可信；升级/回退记录可查；没有自动 V1 fallback。
单品牌先行可作为限定范围发布，但不能据此关闭“五品牌旧能力替换”目标。
