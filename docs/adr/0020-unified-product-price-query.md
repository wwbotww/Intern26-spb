# ADR-0020：以统一 V2 查询核心替换设备价格旧表依赖

- 状态：Accepted；采用本路线进入实施，不表示完整替换或发布已完成。
- 日期：2026-09-11
- 关系：补充 [0006](0006-typed-tool-routing.md) 的类型化路由和
  [0007](0007-v1-v2-api-compatibility.md) 的价格复用方式；保留
  [0012](0012-query-scoped-tool-receipts.md) 的查询级收据边界。
  旧决策的历史实现描述不因路线被接受而视为已被替换。

## 背景

Agent 当前通过 V1 DevicePriceTool 消费旧产品/SKU/现价表。
数据生产者正在把设备采集原生接入已有生鲜使用的 V2 listing/revision/observation 模型，
并补齐设备标准商品与规格关联。只新加一个生鲜 Tool 会留下两套完整价格业务；
只换 SQL 表名则不能正确处理标准商品未填充、报价单位差异和无金额状态。

## 决策

1. 采用一个 `ProductPriceQueryService`、一个 V2 只读 Repository 和统一价格事实模型；
   设备与生鲜使用明确的匹配策略，不复制连接、单位校验、状态处理和来源投影。
2. 设备先做产品硬身份约束，再做产品内规格筛选；依赖可信、有效的规范商品 match。
   生鲜可消费来源归一属性，不强制关联标准品牌/商品；模型不生成 SQL 或可信商品 ID。
3. 最新指针与实际观察分离；原始报价和标准单位价分离；无金额状态不能被旧价格覆盖。
   历史证据保留自己的来源与时间，不将“最近有价”描述为当前报价。
4. 新 Agent 以 `product_price` 承载统一能力，LangGraph 负责有界补槽、候选选择、执行和恢复。
   候选绑定查询与条件；结果澄清不是技术 retry，resume 不重置查询预算。
5. V1 HTTP 设备模式保留薄协议适配，借用新 Service；价格资源生命周期移交应用组合根。
   政策复用不重写，不增加新服务或通用插件框架。
6. API/Web 协调升级并设置显式契约门禁；旧完成结果仍按历史 DTO 读取，不能升级时重新查价。
   无法安全恢复的旧未完成价格查询要求重启，不改写旧参数指纹或猜测迁移。
7. 通过 V1 表不存在或无权限的 MySQL 测试证明解耦。正式新路径不自动 fallback 到 V1；
   回退属于明确的部署/状态快照操作，不能让冻结的旧表悄悄掩盖 V2 数据缺口。

## 未采用的方案

- 两个长期独立 Tool：会重复理解、匹配、失败处理与结果校验，不满足最终旧表替换目标。
- 全部商品套用设备 SKU：会强制不存在的品牌/型号，混淆生鲜地区、批零与计价单位。
- 所有设备只按 listing 标题模糊搜索：丢失既有型号/规格硬约束和生产者标准匹配成果。
- V2 未命中就读 V1：无法证明新链路覆盖，也可能把旧观察作为新报价返回。
- 自动把旧 state/result 改名为新类型：改变指纹和事实含义，破坏重放与历史来源。

## 代价与验收边界

需要同时修改消费者合同、装配、Graph 候选循环、公开 DTO、Web 和 Eval；
只完成 Repository 不能声称全品类 Agent 已交付。首轮限制为设备及已有生鲜来源，
不附带任意日期趋势、采集扩容或 V1 历史迁移。

实施包、预算、兼容策略、数据缺口和 A～E 门禁唯一维护于
[实施计划](../product-price-implementation-plan.md)。消费者字段合同与合成证据见
[价格消费合同](../../apps/assistant-api/docs/integrations/product-price.md)；
真实能力始终以[当前状态](../current-status.md)和对应验收证据为准。
